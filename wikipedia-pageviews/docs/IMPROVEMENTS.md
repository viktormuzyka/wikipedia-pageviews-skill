# Можливі покращення

Документ для тих, хто розвиватиме навичку далі. Пункти впорядковані за пріоритетом. Кожен
спирається на конкретну проблему з прогонів ([evals/results.md](../evals/results.md)) або на
відоме обмеження v1. Опис поточної будови — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Як розвивати: цикл ітерації

Кожне покращення проходить один і той самий цикл, щоб навичка лишалася надійною на дешевій
моделі:

1. **Сценарій.** Додати в `evals/scenarios.md` запит, на якому поточна версія помиляється
   або якого не вміє.
2. **Прогін.** Запустити його на дешевій моделі (Haiku 4.5, безкоштовна модель OpenRouter)
   і записати, що саме пішло не так.
3. **Виправлення в коді.** Спершу змінювати вивід інструмента: логіку, готові речення,
   застереження поруч із числом. Інструкції в SKILL.md — лише коли код не допомагає.
4. **Тест.** Додати офлайн-тест на нове правило.
5. **Повторний прогін** того самого сценарію і запис результату.

Так уже виправлено всі помилки з прогонів: рекомендацію мови з ботами, неоднозначне «0/12
months up», пропущені застереження, відсутній PDF.

## 1. Найближчі покращення (невеликі, висока користь)

| # | Проблема | Рішення |
|---|---|---|
| 1.1 | Звіт займає 9–10 викликів інструментів: прочитати, написати нотатки, запустити `report`, перевірити | `analyze --notes notes.md` або `report` з автоматичним підхопленням останнього запуску — звіт за 2 кроки |
| 1.2 | Переглядів старих назв (редиректів) немає; перейменована у вікні стаття виглядає новою й отримує LOW | Додавати перегляди редиректів через `prop=redirects` (з лімітом), показувати їхню частку |
| 1.3 | Неоднозначні слова: «Mercury» без уточнення стає брендом автомобілів | Якщо англійська сторінка — disambiguation або кілька кандидатів мають статті, друкувати `AMBIGUOUS` зі списком і просити агента уточнити в користувача |
| 1.4 | Питання про професії чи наймання («попит на інженерів комп'ютерного зору») — агент не завжди каже, що стаття про тему лише замінник | Окреме правило в SKILL.md і рядок у LIMITS: «це інтерес до теми, а не попит на фахівців» |
| 1.5 | Коли користувач не назвав мови, агент обирає їх сам і не каже про це | Правило «назвати обрані мови припущенням» і рядок у `ANSWER` |
| 1.6 | Claims-check не бачить якісних тверджень («найвищі показники», «краща економіка») і чисел із пробілом як роздільником тисяч («7 037») | Перевіряти, чи збігаються згадані «найбільша/найкраща мова» з рядком порівняння у FINDINGS; підтримати звичайний пробіл у числах |
| 1.7 | Підписи мов на кінцях ліній графіка інколи накладаються | Розводити підписи по вертикалі, якщо відстань менша за висоту рядка |
| 1.8 | Модель інколи лишає частину FINDINGS англійською або плутає назви мов (`sk` → «словенська») | Друкувати FINDINGS мовою користувача: `--answer-lang uk`, тексти вже є в `TEXT` |

## 2. Якість даних і статистики (середні зміни)

| # | Проблема | Рішення |
|---|---|---|
| 2.1 | Евристика ботів за географією груба (частка США ≥ 25% або Сінгапуру ≥ 10%) | Додати сигнали: частка `automated`/`spider` порівняно з `user`, розрив desktop/mobile, денні сплески лише на desktop |
| 2.2 | Нормалізація «відносно всього розділу» не враховує, що різні тематики падають по-різному (AI-відповіді в пошуку) | Порівнювати з групою схожих статей (peer baseline) з тієї ж категорії Wikidata |
| 2.3 | Змін класифікації ботів і точок зламу в даних не видно | Виявлення точок зламу (changepoint) від 36 місяців даних, прапорець «рівень змінився в місяці X» |
| 2.4 | На 24 точках немає прогнозу | STL-декомпозиція і простий прогноз з інтервалом від 3 років даних |
| 2.5 | Багато мов — ризик випадкового «переможця» | Поправка на множинні порівняння (sign-test p-value вже є в `analysis.json`) |

## 3. Складніші дослідження (нові можливості)

| # | Можливість | Як |
|---|---|---|
| 3.1 | Тема як набір статей, а не одна стаття | Автоматичні кошики через Wikidata SPARQL («усі підкласи X», «instance of»), категорії Wikipedia |
| 3.2 | Пошук тем, що ростуть | Команда `discover`: топ статей мовного розділу за приростом у межах теми або категорії |
| 3.3 | Що читають до і після статті | Датасет Wikipedia Clickstream: пов'язані інтереси аудиторії |
| 3.4 | Від мови до країни | Опублікований Wikimedia датасет переглядів за країнами (з differential privacy): оцінка «країна × стаття» замість «мова × стаття» |
| 3.5 | Незалежне підтвердження | Google Trends, дані магазинів застосунків, активність редакторів Wikipedia як окремі сигнали у звіті |

## 4. Великі обсяги даних

Зараз кожна стаття — окремий запит до API з паузою 0,25 с. Для сотень тем і ~340 мовних
розділів цього мало.

| Етап | Що змінюється |
|---|---|
| 4.1 | Замість API — місячні дампи `pageview_complete` → Parquet |
| 4.2 | Локальна вітрина «QID × мова × місяць» у DuckDB з інкрементальним оновленням раз на місяць |
| 4.3 | Сканування теми по всіх мовних розділах і тисячах тем за секунди, без лімітів API |
| 4.4 | CLI і вивід для агента не змінюються: нове джерело підставляється в `wiki.py` з тими самими структурами даних |
